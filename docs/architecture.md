# 架构与客户端规划

当前依赖方向为：CLI → service → strategies / readers → models。报告层在内存中整理统一结果，仅显式导出时写成 CSV 和 JSON。领域模型与策略不依赖终端、网络、pandas 或操作系统界面。

## 代码职责

| 模块 | 职责 |
| --- | --- |
| `models.py` | 证券、日线、命中记录、扫描结果 |
| `strategies.py` | 区间涨幅、双均线金叉与可选趋势过滤，纯函数 |
| `readers/base.py` | 数据源 Protocol |
| `readers/tdx.py` | 本地 `.day` 与 ZIP 适配 |
| `service.py` | 扫描协调、单股票错误隔离、数据日期过滤 |
| `boards.py` | 支持范围内的板块分类与市场联动选项，不判断上市状态 |
| `names.py` | 可替换的证券名称、上市状态和日期元数据 |
| `reports.py` | 可追踪参数和数据状态的输出 |
| `cli.py` | 参数与退出码；不包含业务规则 |
| `application.py` | 图形界面的分析请求、校验与结果操作 |
| `windows.py` | 菜单栏、三分区界面、动态策略参数、后台分析与导出 |
| `i18n.py` | 中英文界面、帮助和参数错误文案 |

未来图形桌面、Web API 或后台任务应调用 `service.scan()`，而不是模拟 CLI 或重复写一份筛选逻辑。读取器生命周期由调用方管理。

## 客户端边界

- CLI：通过参数调用分析核心。
- Windows EXE：原生 Tk 图形界面，后台线程调用分析核心；队列向主线程传递进度和结果。
- Web：后续增加后端作业接口与前端；共享数据源在服务端，结果使用 JSON 模型。
- Android / iOS / 微信小程序：建议查询后端作业和结果；若需要离线功能，应另行设计数据同步、存储及本地引擎。
- iOS 需在 macOS 构建并处理签名；小程序需 AppID 与合法域名等配置；这些不应伪装成当前已可发布的功能。

APK、IPA 和小程序包还没有实现或构建。`apps` 中的说明是未来入口，不包含占位可执行文件。

## 数据和发布隔离

`repo` 是 Git 仓库边界。源码、测试、小型参考名称表、文档和第三方来源说明放入该目录。行情原始文件、分析产物、可执行文件保存在同级独立目录。构建脚本默认输出到同级 `dist/<平台>`。

发布应先运行测试，再构建并在目标平台验证。当前 Windows 产物为未签名的单文件 GUI 程序；未制作安装器或代码签名。
